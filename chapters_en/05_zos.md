# Chapter 5  Zero-Overhead Scheduling (ZOS): How to Keep the GPU Running Non-Stop

In a traditional synchronous inference engine, every Decode step is a stop-and-wait relay race between the CPU and the GPU:

$$\text{CPU schedules step } N \longrightarrow \text{GPU runs forward + sample for step } N \longrightarrow \text{CPU waits synchronously & processes step } N \text{ outputs} \longrightarrow \text{CPU schedules step } N+1$$

When a model runs on high-compute accelerators like SM100 with CUDA Graphs enabled, the GPU often finishes a Decode step in just a few milliseconds. Yet between finishing step $N$ and receiving the kernel launch for step $N+1$, the GPU must sit idle waiting for the CPU to copy back sampled tokens, update block tables and state machines, select the next batch, and prepare input tensors. Even if the CPU takes only 3 milliseconds, the GPU ends up idling 20%–30% of the time!

To eliminate this inter-step bubble completely, DeepInfer implements **Zero-Overhead Scheduling (ZOS)**. In this chapter, we dissect how DeepInfer resolves the three cascading challenges that arise when the CPU schedules step $N+1$ ahead of time—**before it even knows the sampling outcome of step $N$**.

![Figure 5-1  CPU / GPU Timeline Comparison Between Synchronous Scheduling and Asynchronous Scheduling (ZOS) (generated by minidi/zos.py)](images/plots_en/ch05_zos_timeline.png)

Look at the bottom half of Figure 5-1 (Asynchronous Scheduling / ZOS):

- While the GPU is busy executing **`forward` and `sample` for step $N$**, the CPU does not wait around—it immediately runs **`schedule(N+1)` for step $N+1$** and launches **`forward(N+1)`** directly onto the GPU stream!
- Only after launching `forward(N+1)` does the CPU wait for **step $N$'s sampling completion event**, execute **step $N$'s ledger settlement `post(N)`**, and finally launch **`sample(N+1)` for step $N+1$**.
- As a result, `forward(0) → sample(0) → forward(1) → sample(1) ...` on the GPU stream link together seamlessly like welded train cars, hiding 100% of the CPU scheduling and post-processing overhead inside the shadow of GPU execution!

## 5.2 The Core Challenge: Scheduling Ahead "Blindfolded"

Moving `schedule(N+1)` ahead of `sample(N)` sounds great in principle, but at the moment the CPU schedules step $N+1$, it is essentially flying blind—because the results of step $N$ are still being computed on the GPU, leaving the CPU facing three thorny unknowns:

1. **Unknown 1 (How many blocks should be reserved?)**: Step $N$ is still running on the GPU, so its KV token count has not yet been committed in `process_outputs(N)`. If the CPU calculates block demand from the stale length, step $N+1$ will under-allocate blocks and cause out-of-bounds GPU writes!
2. **Unknown 2 (Where are the input tokens and true context lengths `seqlens_k`?)**: Each request's input token for step $N+1$ is the token just sampled at step $N$; furthermore, when speculative decoding is active, how many draft tokens step $N$ actually accepted—which determines step $N+1$'s true attention context length `seqlens_k`—is known only to the GPU!
3. **Unknown 3 (What if step $N$ already sampled an `EOS` token?)**: If a sequence actually generated an end-of-sequence token `EOS` during step $N$, the CPU does not know that yet when scheduling step $N+1$, so it schedules the sequence into step $N+1$ anyway. How is that extra wasted step cleaned up?

DeepInfer resolves all three unknowns cleanly with a coordinated design spanning the C++ scheduler, the Worker pipeline, and TileLang GPU kernels. Let us first inspect the four-stage pipeline inside `Worker.execute_model_step` (`deepinfer/worker/worker.py` L89–L189):

```{.mermaid caption="Figure 5-2  Four-Stage Asynchronous Pipeline of Worker.execute_model_step (deepinfer/worker/worker.py L89–L189)"}
sequenceDiagram
  participant E as LLMEngine / Scheduler (CPU)
  participant W as Worker (CPU)
  participant G as GPU Compute Stream
  Note over E: 0. schedule(N+1): Schedule ahead carrying step N's in-flight token count
  E->>W: Enter execute_model_step(N+1)
  W->>G: Stage 1: _correct_seqlens_qk + launch forward(N+1)<br/>(GPU kernel reads input tokens from step N output buffer & patches seqlens_k)
  Note over G: GPU executes forward(N+1) immediately after sample(N)

  W->>G: Stage 3: Launch sample(N+1), then CPU runs pre_sampler_sync()

```

> [!IMPORTANT]
> **Iron Rule: The `forbid_cuda_sync()` Guard**
> During Stage 1 (launching `forward`) and Stage 3 (launching `sample`) in Figure 5-2, `ModelRunner` wraps the entire call chain in the context manager `with forbid_cuda_sync():` (`deepinfer/utils.py` L119–L132), setting PyTorch's CUDA sync debug mode to `"error"`. If a single line of code accidentally calls `.item()`, `.cpu()`, or triggers an implicit CPU-GPU synchronization, the engine raises an exception on the spot! This guarantees that outside the explicit `sample_end_evt.synchronize()` in Stage 2, the CPU launch stream is never blocked.

## 5.3 Solution 1: Dual In-Flight Counters (`total_inflight_tokens` and `last_inflight_tokens`)

To solve Unknown 1 (how to calculate block demand and sequence length for step $N+1$ before step $N$ has settled its ledger), `Sequence::ScheduleState` (`csrc/engine/sequence.hpp` L204–L256) maintains two in-flight counters:

```cpp
// csrc/engine/sequence.hpp L241-L256
void start_inflight_step(int token_count) {     // Called at the end of every schedule()
    total_inflight_tokens += token_count;
    last_inflight_tokens = token_count;
}
void finish_inflight_step() {                   // Called at the start of every process_outputs()
    if (total_inflight_tokens == last_inflight_tokens) {
        total_inflight_tokens = 0;
        last_inflight_tokens = 0;
    } else {
        total_inflight_tokens = last_inflight_tokens;
    }
}
```

Many readers look at these lines and ask: **Why can't we use a single `inflight_tokens` variable? Why do we need both `total_inflight_tokens` and `last_inflight_tokens`?**

Trace the timeline in Figure 5-2 and the reason jumps right out: during the brief window after `schedule(N+1)` finishes and before `post_process(N)` runs in Stage 2, **both step $N$ and step $N+1$ are simultaneously in flight**!

Let $k = 1 + \text{nextn} = 6$ be the maximum number of tokens processed per decode step, and watch how the two counters evolve step by step:

1. **At the end of step $N$'s `schedule(N)`**: `start_inflight_step(6)` is called. Only step $N$ is in flight: `total = 6`, `last = 6`.
2. **During step $N+1$'s `schedule(N+1)`**: Step $N$ has not yet run `post_process(N)`! When `_schedule_decode` checks how many physical blocks step $N+1$ requires, `seq.get_num_blocks()` (`sequence.hpp` L292) computes:
   $$\text{Total reserved positions} = \text{get\_len()} + \text{total\_inflight\_tokens}(6) + \text{draft\_tokens}(5) = \text{get\_len()} + 11$$
   By counting both the up to 6 in-flight tokens from step $N$ and the 5 draft tokens for step $N+1$, the scheduler guarantees that the physical block table has sufficient capacity under all possible verification outcomes!
3. **At the end of step $N+1$'s `schedule(N+1)`**: `start_inflight_step(6)` is called again. Now both step $N$ and step $N+1$ are in flight: `total` accumulates to $6 + 6 = 12$, while `last` records the newest step's $6$.
4. **During Stage 2 of step $N+1$, when `post_process(N)` runs**: Right at entry, `finish_inflight_step()` is called. Seeing `total (12) != last (6)`, it knows step $N+1$ is still in flight behind step $N$, so it sets `total = last (6)`—retiring step $N$'s in-flight reservation while keeping step $N+1$'s 6 in-flight tokens intact!

## 5.4 Solution 2: Direct GPU-Side Wiring (`remap`) and `compute_seqlens_k_zos` Length Correction

With block reservation solved, let us tackle Unknown 2: when launching `forward(N+1)`, the CPU has neither the token sampled at step $N$ nor the count of draft tokens accepted at step $N$. What now?

The answer: **the CPU merely builds an index bridge (`remap`), leaving the actual work of populating input tokens and patching `seqlens_k` entirely to GPU kernels!**

In Stage 1 of Figure 5-2, `Worker._correct_seqlens_qk` (`worker.py` L191–L246) invokes the C++ function `prepare_zos_inputs` (`csrc/engine/zos.cpp` L142ff.), comparing the current step's (step $N+1$) sequence list against the previous step's (step $N$) sequence list to produce an index mapping array `remap`:

- If the $i$-th request in the current batch also ran in the previous decode batch at index $j$, then `remap[i] = j`;
- If the $i$-th request in the current batch just entered from `prompted` (so it did not run decode in step $N$), then `remap[i] = -1`.

Armed with `remap[i] = j`, the GPU performs two operations right before `forward(N+1)` runs:

### 1. Moving input tokens directly inside GPU memory
For a newly admitted sequence with `remap[i] == -1`, the CPU already placed its last token into `input_ids`. For a continuing sequence with `remap[i] = j >= 0`, a GPU kernel uses index $j$ to reach directly into the previous step's device output tensors—`prev_sampled_token_ids[j]` and `prev_predict_token_ids[j]`—and copies the newly sampled token and candidate draft tokens straight into step $N+1$'s input slots without ever touching the host CPU!

### 2. Exact formula correction for context length `seqlens_k`
The algebra here is remarkably clean. Suppose that prior to step $N$, a sequence had $C = \text{cache.num\_tokens}$ committed tokens in the KV Cache:

- During step $N$, the sequence always accepts 1 main token plus $A_j = \text{prev\_num\_accepted\_tokens}[j]$ draft tokens ($0 \le A_j \le \text{nextn}$). Thus, the number of valid tokens actually committed to the KV Cache by step $N$ is $1 + A_j$.
- Entering step $N+1$, suppose the variable-length verification kernel decides to verify $Q_i = \text{seqlens\_q}[i]$ query tokens in this step. Then the true context length $\text{seqlens\_k}[i]$ that attention should see in step $N+1$ is:
  $$\text{seqlens\_k}^{\text{true}}[i] = C + (1 + A_j) + Q_i$$
- However, when the CPU calls `prepare_zos_inputs` (`zos.cpp` L188), it knows neither $A_j$ nor the GPU-recomputed $Q_i$. So the CPU initializes `seqlens_k[i]` to a baseline value that assumes "all $\text{nextn}$ drafts from the previous step were accepted, minus the provisional `seqlen_q`":
  $$\text{seqlens\_k}^{\text{CPU\_init}}[i] = C + (1 + \text{nextn})$$
- Moments later on the GPU, the TileLang kernel `compute_seqlens_k_zos` (`layers/tilelang_ops/compute_seqlens_k_zos.py` L22–L23) executes a single in-place correction in device memory:
  $$\text{seqlens\_k}[i] \gets \text{seqlens\_k}^{\text{CPU\_init}}[i] + Q_i - (\text{nextn} - A_j)$$
  Substituting $\text{seqlens\_k}^{\text{CPU\_init}}[i] = C + 1 + \text{nextn}$ cancels out $\text{nextn}$ cleanly, recovering the exact length:
  $$\text{seqlens\_k}[i] = C + (1 + A_j) + Q_i$$

## 5.5 Solution 3: Post-Hoc Invalidation—Gracefully Handling Wasted Steps and In-Flight Preemption

Finally, let us examine Unknown 3: what if a sequence already finished during step $N$, or got preempted while step $N$ was still in flight? How does the engine prevent ledger corruption?

1. **Discarding the extra step when step $N$ hits `EOS`**:
   Suppose sequence `seq` samples `EOS` during step $N$. Because the CPU does not know this yet during `schedule(N+1)`, it schedules `seq` into step $N+1$ and launches `forward(N+1)` on the GPU. Then, in Stage 2 of Figure 5-2, `post_process(N)` receives step $N$'s `EOS` and sets `seq.status = FINISHED_STOPPED`. On the following iteration, when `process_outputs(N+1)` settles the outputs of step $N+1$, it checks `seq.is_finished()` right at the top (`scheduler.hpp` L905–L915) and simply discards the extra tokens computed for `seq` in step $N+1$, never emitting a single spurious token!
2. **Preempted while step $N$ is still in flight (Preempted In-Flight)**:
   Suppose `seq` participated in decode step $N$, but during `schedule(N+1)` physical blocks ran short and the left pointer selected `seq` for `_preempt(seq)`! At that point, `_preempt` has already freed its physical blocks, reset its status to `WAITING`, and pushed it back to the front of `waiting`. Moments later in Stage 2, the GPU outputs from step $N$ arrive—at which point we must **never** commit step $N$'s tokens or advance `num_tokens` on this now-evicted sequence! Both `process_outputs` (`scheduler.hpp` L917–L925) and `process_MTPInfo` (L1214–L1219) enforce a dedicated guard for this exact case:
   ```cpp
   // If this is a decode step but the sequence is currently WAITING, it was preempted while in flight—discard its step output!
   if (!prompt_run && seq.status == SequenceStatus::WAITING) continue;
   ```

In Chapter 13, our `minidi/zos.py` (`ZOSEngine`) implementation reproduces this exact in-flight counter machinery, `remap` wiring, and post-hoc invalidation, and verifies across 20 randomized concurrent workloads that `ZOSEngine` produces token-for-token identical outputs to the synchronous engine.

## 5.6 Two Supporting Engineering Details: CPU Gloo Process Group and Discrete CUDA Graph Buckets

To keep the ZOS pipeline completely free of stalls, DeepInfer includes two critical supporting mechanisms:

1. **When ZOS is enabled, multi-GPU step voting uses a CPU Gloo process group**:
   Recall the cross-DP `allreduce` step vote from Chapter 3. If that `allreduce` ran over the GPU NCCL group, it would have to queue on the GPU stream and wait for the running `forward` pass to finish before returning the vote result—injecting a hard CPU-GPU synchronization right inside `schedule(N+1)` and shattering asynchronous overlap! Therefore, when ZOS is enabled, `llm_engine.py` (L313, L665–L679) switches the scheduler's collective group to a **host-CPU `gloo` process group** (`PG.cpu_data_parallel_group()`), allowing DP ranks to complete microsecond-level step voting directly over the host network without touching the GPU stream.
2. **Discrete CUDA Graph buckets (`build_graph_batch_sizes`)**:
   To eliminate per-kernel Python launch overhead, `cuda_graph_runner.py` (L41–L52) and `dflash_cuda_graph_runner.py` pre-capture a discrete ladder of CUDA Graphs indexed by the total query token count `total_q = sum(seqlens_q)`: powers of two below `interval` (default 8)—`[1, 2, 4]`—followed by multiples of 8: `[8, 16, 24, 32, ..., max_size]`. At runtime, `select(total_q)` uses binary search to pick the smallest captured graph `>= total_q` and pads any unused slots.

Notice the staircase nature of this "step up every 8 tokens" ladder: going from 16 total query tokens to 17 total query tokens jumps up an entire CUDA Graph bucket and increases GPU execution time! That observation leads directly into the theme of Chapter 6: **how can we use draft token confidence scores to pack our verification budget right onto the most cost-effective CUDA Graph bucket boundary?**
